## Run 2 后续：根因诊断（2026-08-25，决定性消融实验）

诊断脚本：`scripts/_diag_temporal_failure.py`（5 变体×2 SNR×20ep）、`scripts/_diag_per_user.py`（逐用户剖析，均未跟踪，可复现）。

**真正的根因不是奖励阈值不可达，而是 Worker 的 d_ratio 输出头死在初始化值 0.5：**

1. **d_ratio ≡ 0.50（死头）**：48000 个用户×时隙样本全部落在 [0.4,0.6)，逐用户均值精确 0.50，与 SNR/用户/时隙无关。`D_k = d_ratio·min(R·τ, Q)`（rsma_env.py:822-825）→ 策略每个时隙恒定丢弃一半可服务比特。
2. **强制 d=1（其余不动）**：delivery 0.632→0.830（15dB）、0.395→0.611（30dB），队列 27→14 / 57→38，溢出率 0.175→0.061 / 0.524→0.328，EE 0.253→0.329 / 0.602→0.924 —— **全部指标严格改善，接近 SDMA（0.887/0.664）**。整个 delivery 失败 = 这一个死头。
3. **总功率恒 24W 是架构性的**：`use_softmax_power_share=True`（config.py:82）下 p 块是 softmax 份额 logits，Σ份额·P_k_max ≡ 24W；eval 环境非分层（hierarchical=False）无 Meta 预算裁剪。p40/p60 强制实验零效（功率/R_sum/delivery 一字不变）。**Worker 在评估口径下没有省总功率的自由度**，只能再分配用户间份额。
4. **历史窗口被完全忽略**：置零 user_embed 历史列（hist0 变体）delivery 0.632→0.655 / 0.395→0.407（20ep 噪声量级）。策略连当前队列都未用于其唯一有效杠杆 d，加 4 步历史无济于事 —— **观测容量不是瓶颈，优化才是**。
5. **死头非奖励最优**：compute_reward 四大项（Dinkelbach EE、√交付效用、backpressure、ΣQ²惩罚，lyapunov.py:342-385）全部随 served 递增 → d=1 严格占优。学不动的原因：① LR 早衰至 2e-5 且每 update KL-stop；② DGPS 惩罚门控在 dr≈0.7 抑制了对 d 最敏感的 overflow/queue 惩罚（实测 799→281）；③ 3K 动作维中 alpha 被 Meta 覆盖（group_level_alpha=True）、p 只能再分配，d-head 梯度信噪比被稀释。

**对基线 best [5, 0.9163] 的解读**：同代码同动作空间，loop 经 22+ 轮白名单超参调优（w_overflow/lr_actor/delivery_threshold 等直接强化 d 梯度）+ partial_resume 累积训练，d-head 有逃逸机会；本机无该 ckpt（Mac 侧），此为机制推断非实证。

**后续方向（按性价比）**：
1. d-head 专项修复：单独更高 LR / 惩罚门控豁免 d 敏感项 / 奖励加线性 served 项；d=1 消融已给出上界 ≈ 接近 SDMA
2. best.pt 选择改按评估口径（周期小规模 eval），训练奖励选择偏向速率型策略
3. 功率架构（softmax 份额 → 可省电）不修，EE 优化无从谈起
4. 从 Mac 取基线 ckpt 做 partial_resume 对比，实证「累积训练 vs 单次训练」假设

## 根因翻案：冻结主干 + 评估丢弃专家头（2026-08-25，执行阶段新证据）

上述「d_ratio 死头」结论**被以下两个发现推翻**：

**发现 A — 从零训练时注意力主干被冻结**：`use_bucket_experts: bool = True` 是 config 默认（config.py:475）。该模式下 PPO 把 shared_trunk_params 的 lr 置 0（ppo.py:27-36），只训 4 个 SNR 桶专家头（lr=1e-4），参考头 user_head 也被冻结（actor_critic.py:456-461）。此模式为「从 best 微调」设计——从零训练等于**在随机初始化的冻结特征上训线性头**。Run 1/2 都踩中此坑。

**发现 B — 评估脚本静默丢弃训练好的专家头**：不可变脚本 `scripts/evaluate_snr_sweep.py` 重建 ActorCriticAttn 时未传 use_bucket_experts（类默认 False，actor_critic.py:368）→ 模型无 expert_heads 子模块 → `load_state_dict(strict=False)` 静默丢掉全部专家头权重 → **两次 0/7 评估测的是随机冻结的 user_head，近似无策略**。

**决定性证据（`scripts/_diag_experts_eval.py`，激活专家头的评估）**：
- 15dB delivery **0.886 ≈ SDMA 0.887**（随机头口径仅 0.632）；d_mean **0.94** —— 训练实际学会了 d→1，「死头」只是评估口径的假象
- 7 点总分 [1, 0.713, -23.06]（仍输基线，但与 0/7 完全不同的失败模式：主要是队列惩罚）
- hist0 无差异的原因也清楚了：主干本就冻结，历史窗口从未参与前向

**注意**：d=1 强制消融（delivery 0.83）与专家头激活评估（0.886）相互印证——策略核心能力其实在，两次「彻底失败」均为评估管线 bug。

## Run 4 复盘：为什么功率自由了策略仍满功率（激励分析，2026-08-26）

修正「没有省电梯度」的表述——EE 一直在奖励里（Dinkelbach 项 `served − q*·P`），问题是**q* 自适应让它在低 SNR 失去杠杆**：

1. **q* 是 EE 的滑动比率**（served/power 的 EMA）：策略功率用得越多 → 平均 EE 分母变大 → q* 被拉低 → 功率罚项变弱 → 维持现状成为不动点。它合理化当前功率而非逼你省电。
2. **低 SNR 下 EE 项梯度恰为零**：噪声受限区速率近似线性于功率（R≈c·P），边际速率 = 平均 EE = q*，`served − q*·P` 对功率的净梯度消失；而交付/队列/backpressure 各项继续推功率向上。高 SNR 对数区 EE 项其实倾向降功率，但积压队列（Q=37、溢出 0.16）让交付项占优。
3. **约束通道同向推功率**：RCPO/Lagrangian 约束的是 delivery ≥ 0.98 下界——罚「送得少」从不罚「用得多」。
4. **协同降压探索不可达**：降压需 24 个 p 输出一致变小，高斯探索在 24 维产生联合方向的概率极低；奖励单调又使策略梯度从不指向那边。
5. **物证**：softmax-OFF 口径下 SDMA 用 8.8W 即达 0.922 delivery（0dB）——「省电且高交付」物理可行，是激励设计问题而非能力/物理问题。

## 下一方向（待实施）：接收天线扩容 N_r 16→32（Run 5，用户提议）

思路：与其在奖励侧硬掰功率行为（lyapunov.py 不可改），不如改变物理工作点。

- 当前配置（config.py:13-14）：上行系统，`N_r=16` 基站接收天线、`N_t=2` 每用户发射天线
- **直接作用**：接收阵列增益 ~N_r，0dB 下每用户有效 SNR 抬升，工作点推向「交付饱和区」——比较重心移到队列/溢出动态（RSMA 已在 20-30dB 证明的强项）
- **间接作用（正中 EE 杠杆问题）**：每瓦比特数上升 → 平均 EE 上升 → **q* 被抬高 → 每瓦功率罚加重**——EE 梯度从「低 SNR 退化」变「有牙」，Run 4 的激励死结被物理参数解开
- 实施约束：
  - 改动通道走 `--n_r` CLI flag + 评估包装器同步补丁（沿用 `--no-softmax-power-share` 的 Config-patch 模式），**不动 config.py 默认值**，保持官方口径完好
  - channel.py 不可变，但 N_r 从 config 读取，改参数零代码、纯 config（白名单内）
  - **新口径与基线 [5, 0.9163] 不可横比**（Run 4 教训：N_r 变则 SDMA 基线同步变化，pass 判据是相对的）；Run 5 的对照是「同 N_r=32 口径下的 SDMA」，评估结论按新口径独立陈述
  - N_r=32 使信道矩阵翻倍，训练时长估计 1.5-2×（~9-12h）
- 预期风险：PPO 与 SDMA 同涨，pass 是相对判据，最终效果是经验问题——但即便 pass 数不升，绝对 EE/delivery 的提升对「长期时隙 RSMA 资源优化」的研究叙事本身就是有效结果

  - 得分 **[0, 0.8000, -27.14, 0.710]** —— **0/7 点全部 fail**（PPO delivery 在每一点都落后 SDMA 0.3~4.0pt，队列全线更高）

- **结论：天线扩容方向证伪**。在此评估协议下，「改物理参数」整条路线（功率架构 Run 4、天线扩容 Run 5）都撞在同一堵墙上：基准自我归一化 + 相对判据。唯一有效杠杆是策略质量本身（Run 3 的 --no-bucket-experts 修复证明了这一点）
- ee_ratio 0.710 略优于 Run 3 的 0.6985（高 SNR 每瓦比特更多），但这是字典序第 4 项，救不了 0/7
- **Run 3 仍是最终最佳结果**：[5, 0.9041, -12.59, 0.6985]（官方不可变口径），追平基线 [5, 0.9163, -11.02, 0.6914] 的 pass 数

## 优化背景审计：文献对照 + 固定流量口径实证（2026-08-27）

用户质疑「SDMA 与 PPO 变化一致」暴露的问题设定缺陷，做 IEEE 文献对照审计。

### 文献惯例（可获取全文的代表）

- **RSMA 上行 xURLLC IIoT (arXiv 2405.16471)**：Poisson 到达，**固定均值 250 kbps，外生，不随容量缩放**；报绝对增益（+31.76% 包长 vs OMA、−44.15% 功率 vs NOMA）
- **DRL-Enhanced RSMA (arXiv 2403.05974, 下行)**：无流量模型（纯物理层加权和速率）；报绝对 sum-rate 曲线，≥12dB 处 ~2dB 增益
- **Energy-Efficient RSMA: DRL Framework (IEEE 10273617)**：EE-RSMA-DRL 主线方向参考
- **Lyapunov drift-plus-penalty + DRL 系**：外生到达 + 队列稳定约束 + 绝对时均代价
- 共性：**到达 = 外生固定过程**（或无流量模型）；**绝对指标 + % 增益**；基线忠实实现自身机制

### 本项目偏离点判定

| 维度 | 文献惯例 | 本项目 | 判定 |
|---|---|---|---|
| 到达模型 | 外生固定 | λ=r(SNR)·cap(SNR,K,N_r)/K 随容量自缩放 | 最大偏离（Run 5 根因） |
| 评价口径 | 绝对指标+% 增益 | 相对 SDMA 的 pass 判据 | 循环内可用，论文不可用 |
| 基线实现 | 各自忠实 | SDMA 走 env.step 动作映射，softmax 口径下 p 块被重解释为份额（rsma_env.py:367-373） | 口径缺陷 |
| EE 定义 | 论文明确定义 | 训练 served−q*·P / 评估 R_sum/P | 需披露对齐 |
| 配对实验（同 seed） | 少数文献 | 是 | 优点，保留 |

2. **双口径披露**：normalized-load（现有，强调公平难度对齐）+ fixed-traffic（文献惯例，绝对增益）；两口径的 PPO 都是 Run 3 同一检查点，无需重训
3. **SDMA 基线语义**：softmax 口径下其「队列加权绝对功率」被份额化重解释，论文须披露或用忠实版重跑（sdma_baseline.py 不在 immutable，可改；会动官方分数基线，optimize-loop 口径维持连续性）
4. **固定 λ 选取**：λ=5.5 过载过深；论文建议取 ρ≈0.7-0.9（中 SNR 容量的 70-90%）或做 λ-sweep，而非沿用 config 旧默认
